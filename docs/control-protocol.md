# 控制消息、逻辑时间与模拟

状态：采用 JSON-RPC 2.0 作为控制消息规范已确认；业务设计需要支持模拟与重放，
不能依赖当前系统墙钟。具体业务方法、时间编码、传输和实现库继续讨论。

## 已确认的标准边界

使用 [JSON-RPC 2.0](https://www.jsonrpc.org/specification) 的请求、响应、错误和
notification 封装，不另造 `command`/`command_id` 外层。
业务 namespace 可以放在 `method` 中，例如候选方法 `recording.start`。
`rpc.` 前缀由标准保留，不能用于业务方法。

这个决定不要求视频、逐帧几何或批量媒体数据使用 JSON，也不选择 HTTP、WebSocket、
WebRTC 或本地 socket。传输上的消息分帧、连接与订阅机制后续确定。
`jsonrpc: "2.0"` 是消息规范版本，不是业务 schema 版本。

## 标准与业务责任的分界

| 标准提供的能力 | 仍需定义的业务语义 |
| --- | --- |
| `method` 与 `params` | 方法、参数类型、作用对象、前置条件与实际 effect。 |
| `id` 关联请求和响应 | 任务身份、幂等性、重试、去重范围与重启恢复。 |
| `result` 或 `error` | 什么算调用成功，业务拒绝原因，以及异步任务失败如何表达。 |
| 无 `id` 的 notification | 哪些事件可推送，如何订阅、重连和恢复当前状态。 |
| 多请求 batch | 不保证调用顺序、原子性或统一生效时刻；这些不能从数组顺序推断。 |

JSON-RPC 的 `id` 不提供只执行一次或自动去重保证。建议控制请求使用字符串 ID，
以免数字精度问题；该约束与业务方法的参数规范后续一起确定。
业务任务可有独立的 `recording_id` 等身份，不因 RPC 结束而消失。
需要安全重试时再规定稳定业务操作身份及重复调用的处理，不机械添加通用 ID 层。

notification 按标准没有响应，参数错误也不会返回。
建议开始、停止等需要执行确认的操作使用 request；断线后的状态恢复不能只依赖通知。
JSON-RPC 本身不提供事件持久化或重放保证。

长任务可在建立任务后返回结果，而不等待最终产物完成。
若采用这种方法定义，RPC 成功只确认任务建立；后续任务失败不是同一调用的第二个响应。
任务进展、完成和失败通过业务状态及可能的事件报告。客户端等待超时也不自动取消任务。

业务错误沿用标准 `error.code/message/data` 结构，遵守保留错误码范围；
业务码及可供程序判断的细节另行定义，不新建平行错误封装。

## 逻辑时间与运行时间

业务时间与机器执行速度分离是设计约束。以下分层为后续接口提供讨论基础：

| 时间类别 | 用途 |
| --- | --- |
| 逻辑/媒体时间 | 录制范围、触发位置、动画进度和控制实际生效位置；模拟中可以暂停、步进或加速。 |
| 运行时单调时间 | 通信、设备和写入等运行保护及性能测量，不冒充内容时长。 |
| 墙钟与原始时间证据 | 日志、来源记录、外部同步依据；经明确映射才能关联业务时间线。 |

逻辑时间需要具有时长单位，不只是事件排序编号。候选表示：

- 时间点使用 `timeline_id + ticks`，由时间线明确有理数 time base。
- 时长使用整数 ticks 与明确 time base，不携带绝对日期。
- 超出 JavaScript 安全整数范围的 ticks 可用十进制字符串编码，精度和最终字段仍待定。

不同时间线之间不能未经映射直接比较或相减。时间线重启、跳转和不连续需要定义身份或
分段规则；时间点也不能替代帧身份。存在延迟窗口后，当前输入位置与当前输出位置不同，
业务方法必须明确作用在哪条时间线上，不能只给一个含糊的 `now`。

实时运行仍需利用硬件时钟维持输出节奏；这与将业务效果建立在可模拟的时间线上并不冲突。
输入停顿时逻辑时间如何推进需单独规定，不能意外禁用设备超时等保护。
测试中也应能控制保护时钟，而不是靠真实等待才能触发超时。

## 模拟与重放的设计要求

真实 SDI、文件回放与模拟输入使用相同业务命令和状态语义，替换输入、时钟等边界，
不引入一套测试专用业务协议。业务应可通过推进逻辑时间、注入帧及异常来验证。

候选验收场景：

- 同一输入和生效记录在实时、加速及步进模式下，录制的逻辑范围和帧关联保持一致。
- 修改系统墙钟不改变内容时长、动画进度或已确定的逻辑触发位置。
- 输入停顿时，可独立推进保护时钟验证超时处理，不让测试或设备无限等待。
- 改变内部批次大小不改变已约定的帧关联和逻辑生效边界；运行时 deadline 故障另行注入。

可重放记录应包含命令实际生效的逻辑位置及必要顺序，而不只是用户操作的墙钟时间。
“尽快生效”的命令在首次运行时可能受资源准备影响；重放时需要使用已解析的生效记录，
不能仅重新发送原请求就承诺相同结果。同一时刻冲突操作的排序和仲裁仍需定义。

验证业务范围、状态与元数据关联，不未经约定要求不同编码器或 GPU 产物逐字节一致。

## 对业务文档的要求

每项控制功能逐步明确输入、effect、结果、错误、逻辑时间依据与可模拟的验证场景。
具体参数不因本文中的示例自动定案；从 [Cam1 输入录制](recording-control.md) 开始细化。
